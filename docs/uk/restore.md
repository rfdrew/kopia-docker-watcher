# <a id="list-trigger-and-restore"></a>list, trigger і restore

Три команди питають запущений watcher, чим він керує, роблять через нього знімок і відновлюють знімок. Вони
виконуються в контейнері watcher через `docker exec` і звертаються до watcher там через його unix-сокет
[`CONTROL_SOCKET`](configuration.md#control_socket):

```bash
docker exec kopia-docker-watcher kopia-docker-watcher list
# or, with docker compose:
docker compose exec watcher kopia-docker-watcher list
```

Їм потрібен запущений watcher: знімок проходить через його чергу, з хуками, простоєм і мінімальним інтервалом
із міток, а відновленню, яке зупиняє контейнери, потрібен watcher, щоб запустити їх знову. Коли жоден watcher не
відповідає, вони завершуються з помилкою «no watcher answers at the control socket» і нічого не роблять. Поки
watcher під час свого запуску чекає на kopia server, вони завершуються з помилкою «the watcher is starting».

Кожна команда завершується з кодом 0 у разі успіху, 1 — коли вона не вдалася або не вдалося звернутися до
watcher, і 2 — у разі помилки використання. `--help` виводить повну довідку з використання.

`CONTAINER` — це ім'я контейнера або початок його ID (щонайменше чотири символи). `PATH` — це шлях джерела, як
його показує `list`, шлях, знімки якого робить kopia server, або шлях із `kopia.path`, перед яким додається
`HOST_PREFIX`.

## list

```
$ docker compose exec watcher kopia-docker-watcher list
PATH                  CONTAINERS  PAUSED  SCHEDULE  NEXT SNAPSHOT     LAST SUCCESS      STATUS  PROBLEM
/host/srv/app         app         no      kopia     2026-10-25 02:00  2026-10-24 02:00  IDLE    -
/host/srv/db          db          no      watcher   2026-10-25 03:00  2026-10-24 03:01  IDLE    -
/host/srv/old         old         yes     kopia     -                 2026-10-20 02:00  IDLE    -
```

Для кожного джерела, яким керує watcher, і кожного шляху, під час останнього звіряння якого виникла проблема:

- `CONTAINERS`: контейнери, через які цей шлях потрапляє в резервну копію, зокрема зупинені.
- `PAUSED`: чи стоїть джерело на паузі через те, що жоден із них не працює.
- `SCHEDULE`: хто робить заплановані знімки. `kopia`: kopia server, за політикою. `watcher`: сам watcher, для
  джерела з [хуками](labels.md#hooks) або [зупинкою чи призупиненням](labels.md#stopping-and-pausing).
  `NEXT SNAPSHOT` — коли настає час наступного; `-`, коли такого немає, наприклад під час паузи.
- `LAST SUCCESS`: початок останнього повного знімка.
- `STATUS`: стан джерела в kopia server (`IDLE`, `PENDING`, `UPLOADING`, …), а за ним — фаза знімка з хуками,
  що виконується, і контейнери, які для нього тримаються зупиненими.
- `PROBLEM`: `yes`, коли під час останнього звіряння шляху виникла проблема; проблеми виводяться після таблиці.

Час указано в часовому поясі контейнера (`TZ`). `--json` виводить те саме у форматі JSON, час — у форматі
RFC 3339. Коли kopia server не відповідає, `list` виводить попередження в stderr і не показує його стан і час.

## trigger

```
$ docker compose exec watcher kopia-docker-watcher trigger app
snapshot of /host/srv/app asked for; waiting for it to end
/host/srv/app: snapshot saved (started 2026-10-24 14:02:11 +02:00, kopia task 2a)
```

`trigger` робить знімок кожного шляху контейнера або одного шляху й чекає, доки він завершиться. Знімок
проходить через чергу watcher, як і знімок під час запуску контейнера:

- з [хуками](labels.md#hooks) запущених контейнерів цього шляху, `kopia.pre-exec` до і `kopia.post-exec` після,
  а також зі [stop-during-backup і pause-during-backup](labels.md#stopping-and-pausing); результат з'являється
  після того, як виконано хуки post-exec. Коли хук pre-exec не вдається, знімок не робиться;
- не раніше, ніж мине `kopia.min-interval` від останнього знімка або відтоді, як watcher востаннє запустив знімок, якщо не
  вказано `--force`. Для шляху враховується найкоротший `kopia.min-interval` його контейнерів;
- не тоді, коли знімок джерела очікує в черзі або вивантажується: враховується саме той знімок, і `trigger` про це
  повідомляє;
- після знімка джерела з хуками, що виконується, і після [відновлення](#restore) цього джерела з `--stop`.

Можливі результати: `snapshot saved`, `nothing changed since the last snapshot, none saved` (з політикою, яка
ігнорує ідентичні знімки), `snapshot saved incomplete or with errors`, `snapshot failed`, `snapshot canceled`,
`no snapshot taken` з причиною, і `failed` з помилкою. `trigger` завершується з кодом 0, коли кожен знімок збережено
або не виявлено змін і жоден хук post-exec не завершився невдало.

`--no-wait` повертає керування, щойно знімок запитано; як він завершився, видно в логу watcher. Переривання
`trigger` зупиняє очікування, а не знімок.

Знімок, який watcher робить вручну, відстежується й описується так само, як інші його знімки, і враховується для
`kopia.min-interval` наступного знімка під час запуску.

## restore

```
$ docker compose exec watcher kopia-docker-watcher restore --target /restore/app app
restoring snapshot 9a1f3c… of root@nas:/host/srv/app, taken 2026-10-24 02:00:03 +02:00 (app), into /restore/app on kopia server
restored 1200 files, 31 directories, 512.0 MiB (task 2b)
restored 4810 files, 120 directories, 1.9 GiB (task 2b)
kopia server's restore task 2b ended: success
restore done: 4810 files, 120 directories, 1.9 GiB restored into /restore/app (kopia task 2b)
```

`restore` відновлює знімок джерела в каталог на kopia server через `POST /api/v1/restore` kopia server і
відстежує завдання відновлення в kopia server, доки воно не завершиться. Завдання видно в KopiaUI у розділі
Tasks, і там його можна скасувати.

### <a id="where-the-files-go"></a>Куди потрапляють файли

**Файли записує kopia server**, а не watcher. `--target` — це шлях усередині контейнера kopia server, як і шляхи
джерел, які показує `list`, а том, на якому він лежить, має бути **змонтований у kopia server із правом запису**.
Том, резервні копії якого kopia server лише створює, зазвичай змонтовано лише для читання, і відновлення в нього
не вдається з помилкою «read-only file system». Є два способи:

- Відновити в окремий каталог, а потім перенести файли самостійно. Надайте kopia server том для цього:

  ```yaml
  services:
    kopia:
      volumes:
        - /var/lib/docker/volumes:/host/var/lib/docker/volumes:ro
        - restore:/restore            # writable, for restores
  volumes:
    restore:
  ```

  ```bash
  docker compose exec watcher kopia-docker-watcher restore --target /restore/app app
  ```

- Відновити на місці, у сам шлях джерела, який тоді треба змонтувати з правом запису: приберіть `:ro` із цього
  монтування, принаймні на час відновлення. Використовуйте `--stop` і `--overwrite` (див. нижче).

Каталог створюється, якщо його не існує. Файли отримують тих власників, права доступу й час, які мали в знімку;
kopia server зазвичай працює від імені root, який може їх установити.

### <a id="which-snapshot"></a>Який знімок

Типово — найновіший повний знімок. Неповні знімки — контрольні точки вивантаження та скасовані знімки — беруться
тільки за їхнім ID. Укажіть знімок останнім аргументом: його ID маніфесту або його початок, щонайменше шість
символів. У контейнері kopia server їх перелічує `kopia snapshot list --all --manifest-id --incomplete --show-identical`;
без `--manifest-id` команда натомість показує ID кореневих об'єктів, яких `restore` не приймає.

```bash
docker compose exec watcher kopia-docker-watcher restore --target /restore/app app 9a1f3c
```

### <a id="nothing-is-overwritten-by-default"></a>Типово нічого не перезаписується

Без `--overwrite` kopia server відхиляє `--target`, який існує й не порожній, ще до того, як щось туди запише, і
`restore` завершується з помилкою «non-empty directory already exists». Відновлюйте в новий або порожній каталог
або передайте `--overwrite`.

З `--overwrite` kopia server відновлює в каталог у тому стані, у якому він є: замінює файли й символьні посилання, які є в знімку,
спочатку записуючи кожен файл у тимчасовий файл і перейменовуючи його, щоб жоден файл не лишився записаним
наполовину. **Файли, яких немає в знімку, лишаються**: відновлення не робить каталог ідентичним знімку. Якщо це
важливо, відновіть у порожній каталог і підмініть ним наявний.

Відновлення, яке не вдалося на півдорозі, лишає файли, які встигло записати.

### <a id="--stop-stop-the-containers-while-restoring"></a>`--stop`: зупинити контейнери на час відновлення

Відновлення під запущеним застосунком може його пошкодити: база даних, у якої відкриті файли, застосунок, який
записує, поки файли змінюються. `--stop` зупиняє запущені контейнери шляху перед відновленням разом із кожним
запущеним контейнером, який залежить від них через `kopia.depends-on`, спочатку залежні, як це робить
[stop-during-backup](labels.md#stopping-and-pausing), і запускає їх знову у зворотному порядку, щойно завдання
відновлення в kopia server завершиться, вдало чи ні. Контейнери, які перезапускаються, як-от під час циклічних
падінь, або призупинені, теж зупиняються й повертаються запущеними:

```bash
docker compose exec watcher kopia-docker-watcher restore --stop --overwrite --target /host/srv/db db
```

- Watcher записує зупинені ним контейнери в `STATE_FILE`, перш ніж їх зупинити. Події їхньої зупинки й запуску
  спричиняє сам watcher: джерело не ставиться на паузу, і знімок під час зупинки чи запуску не робиться.
- Поки триває відновлення, watcher не робить знімків джерела: запитані в нього знімки, зокрема заплановані знімки
  джерела з хуками, чекають, доки відновлення завершиться. **Власний розклад kopia server не стримується**:
  знімок джерела, що працює за розкладом kopia server (`SCHEDULE kopia` у `list`), може бути зроблено посеред
  відновлення. Відновлюйте тоді, коли не настає час жодного знімка, як показує `list`.
- Переривання `restore` зупиняє лише виведення: watcher відстежує відновлення й запускає контейнери, коли воно
  завершиться. Щоб зупинити відновлення, скасуйте його завдання в KopiaUI; тоді контейнери повернуться.
- Жоден контейнер не повертається, поки завдання відновлення в kopia server ще виконується: watcher зберігає
  завдання разом із зупиненими ним контейнерами й питає про нього kopia server, перш ніж запустити будь-який із
  них, кожні 10 секунд, доки завдання не завершиться. Коли watcher зупиняється під час відновлення, він скасовує
  завдання, чекає кілька секунд, щоб kopia server дописав файли, які записує, і запускає контейнери, якщо
  завдання на той час завершилося; інакше вони лишаються зупиненими, і watcher запускає їх після свого
  наступного запуску, щойно завдання завершиться. Після збою watcher завдання в kopia server триває далі, і
  watcher запускає контейнери після свого наступного запуску, щойно завдання завершиться. Завдання, про яке
  kopia server уже не знає, як-от після перезапуску kopia server, вважається завершеним. Поки watcher не може звернутися
  до kopia server, контейнери лишаються зупиненими, і про це записується в лог і
  [надсилається сповіщення](configuration.md#notifications), як про контейнер, який не вдається повернути.
  Скасоване відновлення лишає файли, які встигло записати.
- Контейнер, який тим часом запустив хтось інший, лишається запущеним; контейнер, який не вдається запустити,
  пробують запустити знову, записують про це в лог і надсилають сповіщення, як після знімка.
- `--stop` відхиляється, поки виконується знімок джерела з хуками або інше його відновлення, а також поки
  потрібний йому контейнер тримається зупиненим для знімка: спробуйте знову, коли це завершиться. Для зупинки й
  запуску контейнерів потрібен `POST=1` у docker-socket-proxy (див. [Docker](configuration.md#docker)).

Без `--stop` відновлення, ціль якого збігається зі шляхом джерела або лежить усередині нього, виводить попередження, коли
контейнери цього шляху працюють.

### <a id="output-and-exit-status"></a>Виведення і код виходу

`restore` виводить знімок, який відновлює, перебіг так, як його повідомляє kopia server, і результат. Команда
завершується з кодом 0, коли завдання в kopia server вдалося, і 1 в інших випадках, зокрема коли не вдалося
звернутися до watcher або жоден знімок не підійшов.
