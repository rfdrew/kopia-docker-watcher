# <a id="configuration"></a>Конфігурація

Це український переклад сторінки; першоджерело — англійська версія. Змінюючи англійську сторінку, оновіть цей
переклад у тому самому pull request або напишіть у pull request, що він відстає (див. розділ
[Документація](../../README.uk.md#documentation)).

Watcher налаштовують змінними середовища. Порожня змінна означає те саме, що й незадана, тож файл compose може
передати `${VAR}` далі, не нав'язуючи значення. Пробіли на початку й у кінці значень обрізаються, крім
`KOPIA_SERVER_USERNAME` і `KOPIA_SERVER_PASSWORD`, які беруться як є.

Під час запуску watcher перевіряє кожну змінну й повідомляє про всі проблеми одразу, по одному рядку логу на
кожну, а потім завершується з кодом виходу 1. Під час запуску watcher записує в лог конфігурацію, з якою працює,
без секретів: лише те, чи задано пароль, і лише схему та хост `NOTIFY_WEBHOOK_URL`.

Тривалості задаються у форматі Go: `90s`, `10m`, `1h30m`, `24h`. Одиниці `d` немає; для тижня пишіть `168h`.

Булеві значення на цій сторінці приймають `true`, `True`, `TRUE`, `t`, `T`, `1` і `false`, `False`, `FALSE`, `f`,
`F`, `0`. (У мітках інакше, див. [labels.md](labels.md#booleans).)

## kopia server

### `KOPIA_SERVER_URL`

Адреса kopia server, наприклад `https://kopia:51515`. Обов'язкова.

- Схема має бути `http` або `https`, а URL повинен містити хост.
- Шлях дозволено — для kopia server за зворотним проксі; кінцева скісна риска відкидається.
- Жодних параметрів запиту, фрагмента чи облікових даних в URL: використовуйте змінні нижче.

Звичайний `http://` працює з kopia server, запущеним із `--insecure`. Кожен запит містить пароль, тож
використовуйте його лише в мережі, яку ніхто інший не може прослуховувати.

### <a id="kopia_server_username-and-kopia_server_password"></a>`KOPIA_SERVER_USERNAME` і `KOPIA_SERVER_PASSWORD`

Користувач і пароль вебінтерфейсу kopia server, що надсилаються через HTTP Basic auth: `--server-username` і
`--server-password`, з якими запущено kopia server.

- Лише користувач `--server-username` може використовувати API вебінтерфейсу, який потрібен watcher. Користувачі, додані
  через `kopia server user add`, не можуть: kopia server відповідає 403, і watcher зупиняється з повідомленням
  «kopia server denied access».
- `KOPIA_SERVER_USERNAME` типово дорівнює `kopia` — типовому `--server-username` kopia server, — коли задано
  пароль.
- Ім'я користувача без пароля — помилка.
- Якщо не задано жодної з них, watcher під час запуску видає попередження: це працює лише з kopia server, запущеним із
  `--without-password`.
- Неправильні облікові дані зупиняють watcher під час запуску з повідомленням «kopia server rejected the
  credentials»; повторних спроб він не робить.

Watcher входить так само, як вебінтерфейс, і отримує токен CSRF, тож kopia server не потребує
`--disable-csrf-token-checks`.

### TLS

З URL `https://` watcher перевіряє сертифікат kopia server одним із цих способів. Можна задати щонайбільше одну з
трьох змінних, і лише з URL `https://`.

| Змінна | Перевірка |
|---|---|
| жодної | Системні кореневі сертифікати перевіряють сертифікат та ім'я хоста, як для будь-якого сайту HTTPS. |
| `KOPIA_SERVER_CERT_FINGERPRINT` | Відбиток SHA-256 сертифіката, який пред'являє kopia server, має збігатися. Ланцюжок та ім'я хоста не перевіряються. Використовуйте це для самопідписаного сертифіката kopia server. |
| `KOPIA_SERVER_CA_FILE` | Сертифікат має бути підписаний сертифікатом із цього файлу PEM, який замінює системні кореневі сертифікати, і має бути дійсним для імені хоста з URL. |
| `KOPIA_SERVER_INSECURE_SKIP_VERIFY=true` | Жодної перевірки. Будь-хто між watcher і kopia server може прочитати пароль. |

Відбиток — це шістнадцяткове значення, яке kopia server записує в лог, коли генерує свій сертифікат:

```
SERVER CERT SHA256: 3f0c9d…
```

Великі літери й двокрапки між байтами приймаються, тож значення після `Fingerprint=` у виведенні
`openssl x509 -in tls.crt -noout -fingerprint -sha256` теж підходить. Значення, що починається з `SHA256:`, — формат,
який пропонував README версії на Python, — відхиляється з підказкою: це не той відбиток. Сертифікат, що не
збігається, зупиняє watcher; у логу вказано відбиток, який пред'явив сервер.

Лише з `--tls-generate-cert` kopia server під час кожного запуску генерує новий сертифікат у пам'яті, а отже, і
новий відбиток. Щоб він не змінювався, запустіть kopia server один раз із
`--tls-generate-cert --tls-cert-file … --tls-key-file …`, указавши файли, що зберігаються постійно, а потім
приберіть `--tls-generate-cert`: kopia server відмовляється запускатися, коли цей прапорець задано, а файли вже
існують. Див. [README](../../README.uk.md#requirements) і
[приклад](../../examples/docker-compose.yml).

## <a id="paths"></a>Шляхи

### `HOST_PREFIX`

Додається на початок кожного шляху мітки `kopia.path` і шляху на хості кожного монтування, яке вибирає
`kopia.volumes`, щоб утворити шлях, який kopia server копіює в резервну копію. Типово порожня: шлях
використовується як є.

Мітки вказують шляхи на хості Docker. Задайте `HOST_PREFIX`, коли kopia server бачить файли хоста в іншому
каталозі, наприклад коли його контейнер монтує корінь хоста в `/host`:

```yaml
kopia:
  volumes:
    - /:/host:ro
watcher:
  environment:
    HOST_PREFIX: /host
```

Тоді `kopia.path=/srv/app/data` стає джерелом `/host/srv/app/data`, а том `shop_data` з
`kopia.volumes=data` — джерелом `/host/var/lib/docker/volumes/shop_data/_data`. Якщо каталоги хоста змонтовано за
тими самими шляхами всередині kopia server, як у [прикладі](../../examples/docker-compose.yml), залиште її порожньою.

- Має бути абсолютним шляхом. Кінцева скісна риска відкидається; `/` означає відсутність префікса.
- З префіксом шлях мітки відлічується від нього, тож `srv/app` і `/srv/app` — те саме. `..` не повинно виводити за
  межі префікса.
- Без префікса шлях мітки має бути абсолютним.
- Шлях нормалізується: `/srv/app/` і `/srv//app` дають джерело `/srv/app`.

Самому watcher не потрібно бачити ці шляхи.

### `WATCHER_PATH_PREFIX`

Обмежує джерела, яких може торкатися watcher, тими, що лежать під цим шляхом. Типово порожня: без обмеження.

- Має бути абсолютним шляхом; `/` означає відсутність обмеження.
- Застосовується до шляхів джерел після `HOST_PREFIX`. З `HOST_PREFIX=/host` і `WATCHER_PATH_PREFIX=/host/srv`
  `kopia.path=/srv/app` дозволено, а `kopia.path=/etc` — ні.
- Шлях мітки поза префіксом — помилка мітки: мітки контейнера не застосовуються. `validate` теж про це
  повідомляє.
- Те саме стосується шляху на хості монтування, яке вибирає `kopia.volumes`: з
  `WATCHER_PATH_PREFIX=/var/lib/docker/volumes` у резервну копію потрапляють лише томи контейнера, а не його
  bind-монтування.
- Джерело в `STATE_FILE` поза префіксом, наприклад після звуження префікса, watcher не чіпає: не ставить його
  на паузу, не очищає й не видаляє нічого з ним пов'язаного. Він також забуває власників цього джерела, тож якщо
  префікс знову розширять, джерело лише стоятиме на паузі, доки якийсь контейнер знову не почне його копіювати.

Використовуйте це як запобіжник, коли кілька watcher або watcher і люди спільно користуються одним kopia server:
watcher ніколи не реєструє, не ставить на паузу й не видаляє джерело поза своїм префіксом.

## <a id="labels"></a>Мітки

### `LABEL_PREFIX`

Префікс міток, які читає watcher. Типово `kopia`, тож мітки — `kopia.enable`, `kopia.path` тощо. З
`LABEL_PREFIX=backup` вони — `backup.enable`, `backup.path`, …

Літери, цифри, `.`, `-` і `_`, на початку й у кінці — літера або цифра. Мітки без префікса ігноруються. Див.
[labels.md](labels.md).

Зміна префікса в робочому розгортанні призводить до того, що контейнери зі старими мітками втрачають свої шляхи:
їхні джерела ставляться на паузу. Watcher не очищає їх, доки ці контейнери ще існують; з
`kopia.cleanup-on-remove=policy` або `all` він записує в лог, що їхні мітки більше не вказують цей шлях, і
питає, чи не змінилися `LABEL_PREFIX`, `HOST_PREFIX` або `WATCHER_PATH_PREFIX`.

## <a id="behavior"></a>Поведінка

### `RECONCILE_INTERVAL`

Як часто watcher звіряє всі шляхи, на додачу до реакції на події контейнерів. Типово `5m`, мінімум
`10s`.

Повне звіряння підхоплює те, що пропустила подія, повторює спроби для шляхів, мітки яких kopia server відхилив,
описує заплановані знімки й повертає поля з міток, змінені у вебінтерфейсі (розклад і паузу; див.
[migration.md](migration.md#behavior-changes)). Кожен запис політики змушує kopia server оновлювати весь
репозиторій, але watcher записує політику лише тоді, коли вона змінюється.

### `SNAPSHOT_ON_WATCHER_START`

Якщо `true`, перше повне звіряння після запуску watcher вважає кожен запущений контейнер щойно запущеним:
ті, що мають `kopia.snapshot-on-start=true`, отримують знімок, хіба що від останнього знімка ще не минув їхній
`kopia.min-interval`. Типово `false`: перезапуск watcher не робить знімків, на відміну від версії на Python.

### `CLEANUP_GRACE`

Скільки часу джерело має пробути без жодного контейнера, перш ніж `kopia.cleanup-on-remove=policy` або `all`
видалить щось, пов'язане з ним. Типово `24h`, мінімум `10m`.

Час відлічується від моменту, коли watcher уперше бачить, що жодного контейнера, якого він пам'ятає як
власника, більше не існує: контейнер видалено, а не лише зупинено, бо зупинений контейнер і далі володіє своїм
джерелом. Після простою watcher цим моментом стає мить, коли він це помітить. Контейнер, створений заново
під іменем власника, вважається тим самим власником. Контейнер, який знову вказує цей шлях до завершення відстрочки, скасовує
очищення. Див. [labels.md](labels.md#cleanup).

### `STATE_FILE`

Де watcher зберігає те, що мусить пам'ятати: застосовані ним поля політики, розклад, який замінила пауза,
знімки, на які він чекає, і які контейнери володіють кожним джерелом разом із режимом очищення, що його
запитали їхні мітки. Типово `/var/lib/kopia-docker-watcher/state.json`.

- Розмістіть його каталог на томі. В образі `/var/lib/kopia-docker-watcher` належить користувачу, від імені
  якого працює watcher, тож іменований том, змонтований туди, доступний для запису. Не робіть bind-монтування
  окремого файлу: watcher атомарно замінює файл через тимчасовий файл у тому самому каталозі.
- Watcher записує файл під час запуску й зупиняється, якщо не може.
- Він ставить блокування на `STATE_FILE.lock`: файлом стану може користуватися лише один watcher. `run --dry-run`
  читає файл без блокування й нічого не записує.
- Файл, що не є правильним станом (некоректний JSON, немає версії), копіюється вбік як
  `STATE_FILE.corrupt-<time>`, і watcher запускається з порожнім станом. Записи, які не вдається прочитати,
  відкидаються, а файл так само копіюється вбік.
- Файл, записаний новішою версією watcher, зупиняє його під час запуску, і `run --dry-run` так само: запустіть новіший
  watcher або перенесіть файл деінде. Те саме робить файл, який watcher узагалі не може прочитати, наприклад
  файл без дозволу на читання.

Втрата стану не фатальна, але тоді watcher поводиться з кожним джерелом як із таким, що бачить уперше:
він не знає розкладу, який замінила пауза, тож знімає джерело з паузи лише з розкладом із міток, і не пам'ятає
контейнерів, видалених тим часом, тож залишає їхні джерела як є й ніколи їх не очищає.

### `CONTROL_SOCKET`

Unix-сокет, через який команди `list`, `trigger` і `restore` звертаються до запущеного watcher. Типово
`control.sock` у каталозі `STATE_FILE`, в образі — `/var/lib/kopia-docker-watcher/control.sock`.

- Команди запускаються в контейнері watcher через `docker exec` і читають `CONTROL_SOCKET` або `STATE_FILE`
  з того самого середовища, тож знаходять сокет без параметрів. Див. [restore.md](restore.md).
- Під'єднатися може лише користувач, від імені якого працює watcher: сокет створюється в тимчасовому каталозі,
  куди може зайти лише цей користувач, отримує режим `0600` і лише потім переміщується на місце, хоч би яким
  був umask. Його каталог створюється з режимом `0700`, якщо його немає.
- Watcher обслуговує сокет від свого запуску; доки kopia server не готовий, команди отримують «the watcher is
  starting». Він видаляє сокет, коли зупиняється. Сокет, що лишився від watcher, який аварійно завершився,
  замінюється; watcher, який ще відповідає за цим шляхом, або файл там, що не є сокетом, не дає новому watcher
  обслуговувати сокет.
- Watcher, який не може обслуговувати сокет, записує помилку в лог і працює далі без нього; команди тоді
  завершуються помилкою «no watcher answers». Шлях, заданий у `CONTROL_SOCKET`, який не є абсолютним, довший,
  ніж уміщає адреса unix-сокета (103 байти), або лежить у каталозі, довшому за 89 байтів (тимчасовий каталог
  теж має вміститися), є помилкою конфігурації; задовгий типовий шлях поруч зі `STATE_FILE` — лише
  попередження, тож тоді задайте `CONTROL_SOCKET`.
- Сокет — це файл: розмістіть його у файловій системі, що підтримує unix-сокети. Іменований том або
  bind-монтування локального каталогу їх підтримує; деякі мережеві файлові системи — ні.

Нічого, що керує watcher, на `LISTEN_ADDR` не обслуговується.

### `LISTEN_ADDR`

Адреса HTTP-сервера watcher. Типово `:8080`. Він обслуговує:

- `GET /healthz`, стан watcher: див. [Перевірка стану](#health-check).
- `GET /metrics`, метрики Prometheus: див. [metrics.md](metrics.md).

Жоден із них не має автентифікації чи TLS, а метрики називають шляхи ваших джерел і контейнери: тримайте адресу
в мережі, якій ви довіряєте, і не публікуйте порт за її межами.

`HEALTHCHECK` образу запускає `kopia-docker-watcher healthcheck`, який читає `LISTEN_ADDR` і запитує там
`/healthz`, на loopback-адресі, коли `LISTEN_ADDR` слухає всі інтерфейси (`:port`, `0.0.0.0`,
`[::]`). `run --dry-run` не обслуговує HTTP.

### <a id="health-check"></a>Перевірка стану

`GET /healthz` відповідає станом трьох компонентів у JSON:

| Компонент | Чим перевіряється | Не проходить, коли |
|---|---|---|
| `kopia` | запитом до kopia server про стан його репозиторію кожні 15 секунд; поки watcher чекає на kopia server під час запуску — його спробами | kopia server не відповідає, відхиляє watcher або не має під'єднаного репозиторію |
| `docker` | пінгом демона Docker кожні 15 секунд (`GET /_ping`, який docker-socket-proxy типово дозволяє) | Docker не відповідає |
| `reconcile` | переглядом черги звіряння кожні 15 секунд | прохід триває довше за подвоєний `RECONCILE_INTERVAL`, але щонайменше 10 хвилин, або шляхи чекали стільки ж, поки жоден прохід не завершився |

Перевірки виконуються у фоні, тож `/healthz` відповідає відразу, а його опитування нічого не коштує kopia server
і Docker. Компонент стає `failing`, коли його перевірки не проходять 45 секунд без жодного успіху між ними, тож
один втрачений запит не враховується. Доки watcher не дістався kopia server, `docker` і `reconcile` мають стан
`pending`, що не є збоєм; тоді про стан свідчить `kopia`.

| `status` | HTTP | Коли |
|---|---|---|
| `ok` | 200 | жоден компонент не в стані збою |
| `starting` | 200 | протягом 2 хвилин від запуску, поки компонент у стані збою або очікування |
| `unhealthy` | 503 | компонент у стані збою після перших 2 хвилин |

```json
{
  "status": "unhealthy",
  "components": {
    "docker": {"status": "ok", "last_ok": "2026-10-23T12:00:15Z"},
    "kopia": {
      "status": "failing",
      "error": "kopia server: GET /api/v1/repo/status: dial tcp 172.18.0.2:51515: connect: connection refused",
      "last_ok": "2026-10-23T11:58:45Z",
      "failing_since": "2026-10-23T11:59:00Z"
    },
    "reconcile": {"status": "ok", "last_ok": "2026-10-23T12:00:15Z"}
  }
}
```

`error` показує останню невдалу перевірку й тоді, коли компонент ще `ok`. Збій чи відновлення компонента
записується в лог один раз, як «health check failing» і «health check passes again». `HEALTHCHECK` образу позначає
контейнер як unhealthy після трьох невдалих перевірок з інтервалом 30 секунд; watcher у стані unhealthy працює
далі й відновлюється сам, щойно kopia server або Docker знову стануть доступними.

### `LOG_LEVEL`

`debug`, `info` (типово), `warn` або `warning`, `error`, у будь-якому регістрі. `critical` і `fatal`, які приймала
версія на Python, означають `error`. Логи — це рядки JSON у stderr.

## <a id="notifications"></a>Сповіщення

Watcher може надсилати сповіщення, коли шлях починає давати збої і коли він знову працює. Це доповнює профілі
сповіщень kopia server, які повідомляють про знімки, що kopia server робить за своїм розкладом; watcher
повідомляє про те, що бачить лише він:

- **знімок, зроблений watcher**, який завершився помилкою або результат якого невідомий, бо kopia server втратив
  його з поля зору, наприклад коли він перезапустився. Наступний знімок цього шляху від watcher, що завершується успішно
  або нічого не зберігає, бо нічого не змінилося, надсилає «works again». Неповні й скасовані знімки нічого
  не змінюють;
- **[хук](labels.md#hooks), що завершився помилкою**: команда `kopia.pre-exec`, після якої знімок не зроблено,
  або команда `kopia.post-exec`. Кожен хук кожного контейнера відстежується окремо; його наступний успішний запуск
  надсилає «works again». Контейнер, який більше не робить резервну копію шляху або більше не має хуків,
  забувається;
- **контейнер, який watcher [зупинив або призупинив](labels.md#stopping-and-pausing) для знімка й не може
  повернути**. Watcher продовжує спроби; щойно контейнер знову запрацює, бо його запустив watcher або хтось інший,
  він надсилає «works again». Коли watcher припиняє спроби, бо контейнер видалено або хтось інший запустив чи
  зупинив його, «works again» про це повідомляє;
- **мітки, які не вдається застосувати** до шляху: kopia server відхиляє розклад, політику чи шлях, контейнери,
  що мають спільний шлях, не узгоджуються між собою, мітки контейнера містять помилки або `STATE_FILE` відмовляє
  у зміні. Перший прохід, що застосовує мітки, надсилає «works again».
- **збої kopia server для шляху**, що тривають довше за `NOTIFY_ERROR_AFTER`, після запуску watcher, і збої
  Docker для шляху, прохід якого саме виконувався. Watcher повторює спроби; якщо повторна спроба вчасно вдається,
  нічого взагалі не надсилається.

Демон Docker, що не працює, і kopia server, до якого watcher не може дістатися під час запуску, не дають watcher
обробляти жодного шляху, тож вони не надсилають сповіщень: їх видно в [перевірці стану](#health-check) і в
[`kopia_watcher_reconcile_errors_total`](metrics.md#kopia_watcher_reconcile_errors_total)`{kind="docker"}`.

Кожен шлях надсилає одне сповіщення, коли починає давати збої, і одне, коли знову працює, а не по одному на
кожну спробу й не повторно під час кожного повного звіряння. Watcher зберігає це лише в пам'яті: про проблему, що
триває й після перезапуску watcher, буде повідомлено ще раз.

Сповіщення чекають у черзі й надсилаються по одному, тож watcher ніколи не чекає на вебхук. На кожну спробу
відведено 10 секунд. Невдалу спробу повторюють через 2, 4 і 8 секунд або через час із `Retry-After`, який запитує вебхук,
але не більше хвилини, якщо вебхук не відповів, відповів 408 чи 429 або відповів кодом 5xx; будь-яка інша відповідь
одразу вважається невдачею. Коли в черзі чекають 64 сповіщення, нові відкидаються; під час зупинки ті, що
чекають, відкидаються. [`kopia_watcher_notifications_total`](metrics.md#kopia_watcher_notifications_total)
їх підраховує. Переспрямувань watcher не виконує.

### `NOTIFY_WEBHOOK_URL`

Куди надходять сповіщення: URL `http://` або `https://` з хостом і без фрагмента; рядок запиту дозволено. Якщо
змінну не задано, сповіщення не надсилаються. Користувач і пароль в URL (`https://user:pass@host/…`)
надсилаються як HTTP Basic auth.

URL може містити токен, тому watcher ніколи не записує його в лог: лог запуску, рядки логу про сповіщення та їхні
помилки показують лише його схему й хост.

### `NOTIFY_WEBHOOK_FORMAT`

Як надсилається сповіщення. Типово `json`.

| Формат | URL | Запит |
|---|---|---|
| `json` | будь-який | `POST` об'єкта JSON нижче, `Content-Type: application/json` |
| `ntfy` | тема, напр. `https://ntfy.sh/my-backups` | [запит публікації](https://docs.ntfy.sh/publish/): повідомлення як тіло, `Title`, `Priority` (`high` для збою, `default` для відновлення) і `Tags` (`warning`, `white_check_mark`) як заголовки |
| `slack` | [вхідний вебхук](https://api.slack.com/messaging/webhooks), `https://hooks.slack.com/services/…` | `{"text": "*title*\nmessage"}` |
| `telegram` | `https://api.telegram.org/bot<token>/sendMessage?chat_id=<chat>` | [`sendMessage`](https://core.telegram.org/bots/api#sendmessage) з параметрами рядка запиту, такими як `chat_id` і `message_thread_id`, і текстом у тілі JSON; сам рядок запиту не надсилається |

Для ntfy з токеном доступу вкажіть його в URL як
[параметр запиту `auth`](https://docs.ntfy.sh/publish/#query-param) або використайте користувача й пароль в URL.
Для `telegram` URL без `sendMessage` або без `chat_id` є помилкою конфігурації.

Формат `json` надсилає:

```json
{
  "event": "snapshot_failed",
  "status": "failing",
  "title": "Backup failed: /srv/app/data",
  "message": "The snapshot of /srv/app/data on nas (app-db-1) failed: unable to read directory: permission denied.",
  "path": "/srv/app/data",
  "containers": ["app-db-1"],
  "host": "nas",
  "reason": "failed",
  "error": "unable to read directory: permission denied",
  "since": "2026-10-23T03:00:12Z",
  "time": "2026-10-23T03:00:12Z",
  "watcher_version": "v0.2.0"
}
```

| Поле | Значення |
|---|---|
| `event` | `snapshot_failed`, `snapshot_recovered`, `hook_failed`, `hook_recovered`, `return_failed`, `return_recovered`, `reconcile_failed` або `reconcile_recovered` |
| `status` | `failing` або `resolved` |
| `title`, `message` | текст, який надсилають інші формати |
| `path` | шлях джерела |
| `containers` | контейнери, що роблять резервну копію шляху, якщо watcher ним керує; може бути порожнім |
| `host` | ім'я хоста kopia server, яке мають його джерела |
| `reason` | для знімка — його результат (`failed`, `unknown`, `succeeded`, `identical`); для хука — `pre-exec` або `post-exec`; для поверненого контейнера — `stop` або `pause`; для міток — вид помилки, як `kind` у [`kopia_watcher_reconcile_errors_total`](metrics.md#kopia_watcher_reconcile_errors_total); порожнє для `reconcile_recovered` |
| `container` | для хука — контейнер, у якому він виконувався; для `return_failed` і `return_recovered` — сам контейнер; для інших подій відсутнє |
| `error` | що пішло не так, щонайбільше 1000 символів; порожнє для відновлення |
| `since` | коли шлях почав давати збої |
| `time` | коли створено сповіщення |

### `NOTIFY_ERROR_AFTER`

Скільки має тривати для шляху помилка, після якої watcher повторює спроби, наприклад недоступність kopia server, без успішного
проходу між спробами, перш ніж watcher надішле про неї сповіщення. Типово `15m`, мінімум `1m`. Про помилки, після
яких watcher не повторює спроб, наприклад розклад, який відхиляє kopia server, і про проблеми з мітками сповіщення
надсилається одразу.

Поки kopia server не працює, збій дає кожен шлях, тож кожен шлях, який обробляє watcher, надсилає власне
сповіщення.

## <a id="throttle"></a>Обмеження швидкості

Змінні `KOPIA_THROTTLE_` задають обмеження kopia server для сховища його репозиторію через
`PUT /api/v1/repo/throttle`, як це робить вебінтерфейс Kopia. Якщо їх не задано, watcher не чіпає обмежень:
використовуйте це **лише тоді, коли ними більше ніщо не керує**, наприклад ресурс `kopia_throttle` провайдера
Terraform (див. [terraform.md](terraform.md)). Щойно задано будь-яку з них, watcher володіє обмеженнями, які
задає, і повертає їх під час кожного запуску.

| Змінна | Поле Kopia | Значення |
|---|---|---|
| `KOPIA_THROTTLE_UPLOAD_BYTES_PER_SECOND` | `maxUploadSpeedBytesPerSecond` | байтів за секунду |
| `KOPIA_THROTTLE_DOWNLOAD_BYTES_PER_SECOND` | `maxDownloadSpeedBytesPerSecond` | байтів за секунду |
| `KOPIA_THROTTLE_READS_PER_SECOND` | `readsPerSecond` | читань сховища за секунду |
| `KOPIA_THROTTLE_WRITES_PER_SECOND` | `writesPerSecond` | записів у сховище за секунду |
| `KOPIA_THROTTLE_LISTS_PER_SECOND` | `listsPerSecond` | переліків сховища за секунду |
| `KOPIA_THROTTLE_CONCURRENT_READS` | `concurrentReads` | одночасних читань |
| `KOPIA_THROTTLE_CONCURRENT_WRITES` | `concurrentWrites` | одночасних записів |

- `0` означає відсутність обмеження, тож `KOPIA_THROTTLE_UPLOAD_BYTES_PER_SECOND=0` знімає раніше задане
  обмеження.
- Швидкості — це числа, дробові дозволено. Швидкості в байтах приймають одиницю: `k`, `M`, `G` або `T` для
  степенів 1000, `Ki`, `Mi`, `Gi` або `Ti` для степенів 1024, з `B` або без, у будь-якому регістрі: `500k`,
  `10MB`, `10MiB`. Це байти, а не біти.
- Коли kopia server готовий, watcher читає обмеження, задає ті, що вказані в змінних, залишає інші такими, як
  вони є в kopia server, і записує лише тоді, коли щось змінюється. kopia server зберігає їх у конфігурації свого
  репозиторію, тож вони переживають його перезапуски. Спроба, що зазнала збою, який kopia server може подолати, повторюється
  під час наступного повного звіряння.
- kopia server, під'єднаний до сервера репозиторію замість сховища, не має обмежень, які можна задати; watcher
  записує помилку в лог і працює далі.

## Docker

Watcher звертається до Docker так само, як docker CLI: `DOCKER_HOST`, `DOCKER_API_VERSION`, `DOCKER_CERT_PATH` і
`DOCKER_TLS_VERIFY`. Якщо їх не задано, він використовує локальний сокет `/var/run/docker.sock`. З
docker-socket-proxy задайте `DOCKER_HOST=tcp://docker-socket-proxy:2375`.

Що watcher запитує в Docker:

| Запити | Для чого | docker-socket-proxy |
|---|---|---|
| `GET /containers/json`, `GET /containers/{id}/json` | контейнери та їхні мітки | `CONTAINERS=1` |
| `GET /events` | події контейнерів | `EVENTS=1` |
| `GET /_ping`, `GET /version` | перевірка стану й версія API | дозволено типово |
| `POST /containers/{id}/exec`, `POST /exec/{id}/start`, `GET /exec/{id}/json` | лише [хуки](labels.md#hooks) | `EXEC=1` і `POST=1` |
| `POST /containers/{id}/stop`, `/start`, `/pause`, `/unpause` | лише [зупинка та призупинення](labels.md#stopping-and-pausing) | `CONTAINERS=1` і `POST=1` |

Без хуків, `kopia.stop-during-backup` і `kopia.pause-during-backup` watcher лише читає, і проксі може залишити
`POST=0`. З ними йому потрібен `POST=1`, який проксі далі не звужує: тоді він пропускає кожен `POST` до
дозволених розділів, тож із `CONTAINERS=1` — також створення й видалення контейнерів. Це все одно менше, ніж
сам сокет, який дозволяє все. Watcher, який отримує 403 на зупинку, не робить знімка й записує помилку в лог;
той, що отримує його на запуск, продовжує спроби, доки проксі це не дозволить.

Виведення хука надходить через оновлене з'єднання `POST /exec/{id}/start`, яке docker-socket-proxy пропускає,
але закриває, коли ним нічого не передавалося 10 хвилин (`timeout client` і `timeout
server` у HAProxy; у власному проксі задайте `timeout tunnel`, щоб збільшити цей час). Хук, який мовчить довше,
наприклад `pg_dump -f` великої бази даних, усе одно працює: коли виведення обривається раніше, watcher кожні кілька
секунд запитує в Docker, чи завершилася команда, аж до `kopia.hook-timeout`. Лише виведення після обриву не
записується в лог.

Якщо `DOCKER_API_VERSION` не задає версію API, watcher узгоджує її з демоном; підходить будь-який демон з API
1.40 (Docker 19.03) або новіший. [Перевірка стану](#health-check) пінгує демон (`/_ping`).

| Змінна | У watcher |
|---|---|
| `KOPIA_EXEC_CONTAINER` | **Помилка.** Watcher відмовляється запускатися: він спілкується з kopia server лише через його HTTP API й ніколи не запускає `kopia` в контейнері. Видаліть змінну й задайте `KOPIA_SERVER_URL`. |
| `KOPIA_PASSWORD` | **Ігнорується з попередженням.** Це пароль репозиторію; kopia server сам відкриває репозиторій і потребує його, а watcher — ні. Задайте його лише для kopia server. |
