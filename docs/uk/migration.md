# <a id="migrating-from-kopia-docker-operator"></a>Перехід із kopia-docker-operator

kopia-docker-watcher замінює `kopia-docker-operator`, написаний на Python. Обидва реєструють шляхи контейнерів як
джерела в kopia server через його HTTP API, тож watcher переймає джерела, які зареєстрував operator, разом з
історією їхніх знімків.

**Мітки ваших застосунків лишаються як є.** Імена, типові значення й булеві значення `kopia.enable`,
`kopia.path`, `kopia.schedule`, `kopia.snapshot-on-start`, `kopia.snapshot-on-stop`, `kopia.description` і
`kopia.tags` ті самі. **Змінюється розгортання самого watcher**, а також дещо в поведінці.

## <a id="what-changes-in-the-deployment"></a>Що змінюється в розгортанні

| Operator на Python | Watcher |
|---|---|
| Працює від root і читає `/var/run/docker.sock` | Працює від користувача 65532: додайте групу сокета через `group_add` або використайте docker-socket-proxy з доступом на читання до `containers` і `events`. Див. [приклад](../../examples/docker-compose.yml). |
| Без стану | Потрібен том для `STATE_FILE` у `/var/lib/kopia-docker-watcher`. |
| `KOPIA_PASSWORD` у його середовищі | Не потрібен: репозиторій відкриває kopia server. Watcher попереджає, якщо змінну задано. |
| Томи з даними (`/var/lib/docker/volumes`, `/:/host`) і том конфігурації kopia | Не потрібні: файли читає kopia server. Приберіть їх. |
| `KOPIA_EXEC_CONTAINER` (режим exec) | Вилучено. Watcher відмовляється запускатися, поки змінну задано. |
| `KOPIA_SERVER_CERT_FINGERPRINT` вимикав перевірку TLS незалежно від значення | Відбиток перевіряється. Це шістнадцяткове значення після `SERVER CERT SHA256:` у логу kopia server, а не значення `SHA256:…`, яке радив README operator. Значення, що працювало раніше, найімовірніше, тепер неправильне. |
| kopia server потребував `--disable-csrf-token-checks`, щоб виклики API працювали | Не потрібно: watcher сам обробляє токени CSRF. Прапорець можна прибрати. |
| Образ `rfdrew/kopia-docker-watcher:0.1.0` у Docker Hub | Watcher публікується в тому самому репозиторії Docker Hub і як `ghcr.io/rfdrew/kopia-docker-watcher`, з тегами з [README](../../README.uk.md#image). Реліз watcher 0.1.0 займає тег `0.1.0`, який був тегом operator. |
| — | `stop_grace_period` 10 с або більше (типове значення) дає watcher змогу зберегти стан під час завершення роботи. |

`KOPIA_SERVER_URL`, `KOPIA_SERVER_USERNAME`, `KOPIA_SERVER_PASSWORD`, `HOST_PREFIX` і `LOG_LEVEL` зберігають своє
значення. **Лишіть `HOST_PREFIX` таким, як був**, щоб шляхи джерел не змінилися: з іншим префіксом watcher
реєструє нові джерела, а старі разом зі своїми знімками втрачають свої контейнери.

Сам kopia server має відповідати [вимогам](../../README.uk.md#requirements): увімкнений вебінтерфейс, облікові дані
watcher — це `--server-username` і `--server-password`, шляхи видимі, стабільне ім'я хоста й постійний
сертифікат TLS.

## <a id="behavior-changes"></a>Зміни в поведінці

- **Перезапуск watcher не робить знімків контейнерів, які й далі працювали.** Operator під час кожного свого
  перезапуску робив знімок кожного запущеного контейнера з `kopia.snapshot-on-start=true` (типове значення).
  Задайте `SNAPSHOT_ON_WATCHER_START=true`, щоб зберегти таку поведінку, з обмеженням частоти через
  `kopia.min-interval`. Контейнери, що запустилися чи зупинилися, поки watcher не працював, і запущені
  контейнери, чиє джерело operator лишив на паузі, як і раніше отримують свій знімок під час запуску чи зупинки
  на першому проході.
- **Знімки під час запуску обмежені за частотою.** Запуск контейнера робить знімок, лише якщо з останнього минуло
  `kopia.min-interval` (типово `10m`) і не тоді, коли вже виконується інший. Знімки під час зупинки не обмежені.
- **`kill` — це не зупинка.** Operator вважав `docker kill -s HUP` зупинкою й ставив на паузу джерело
  запущеного контейнера. Зупинкою вважається лише `die` контейнера, який після цього лишається зупиненим. Контейнер, що циклічно
  падає й перезапускається своєю політикою перезапуску, не ставить своє джерело на паузу й не робить знімків під
  час зупинки.
- **Теги потрапляють в опис.** Operator записував `kopia.description`, `kopia.tags` і власні мітки
  (`managed-by`, `container`, `compose-project`) у `policy.labels`, а це поле kopia server мовчки відкидає, тож нічого
  з цього так і не з'являлося. Watcher записує опис кожного знімка, а після нього теги у вигляді
  `[key=value …]`, бо kopia server поки не вміє задавати теги знімків через свій API. Він також описує
  заплановані знімки, зроблені після того, як він почав керувати джерелом; старіші знімки лишаються як є.
- **Паузи operator знімаються.** Operator ставив джерело на паузу під час кожної зупинки й `kill` і знімав паузу
  лише під час наступної події запуску; джерела контейнерів, що зараз працюють, можуть досі бути на паузі.
  Watcher визначає паузу лише за станом контейнерів: джерело запущеного контейнера знімається з паузи під час
  першого проходу, джерело, всі контейнери якого зупинені, ставиться на паузу. Оскільки watcher не знає розкладу,
  який замінила така пауза, він знімає паузу з розкладом із міток. Пауза, яку ви поставили у вебінтерфейсі на
  шлях запущеного контейнера, теж знімається.
- **Поля з міток відновлюються; інші зміни у вебінтерфейсі зберігаються.** Operator під час кожного запуску й
  зупинки замінював політику повністю, тож правила зберігання, стиснення й ігнорування, задані у вебінтерфейсі,
  губилися. Watcher об'єднує зміни: він записує лише `scheduling.cron` (з `kopia.schedule`, `0 * * * *`, коли жодна
  мітка не задає розклад), паузу й поля [міток політики](labels.md#policy-labels), яких operator не мав.
  Усе інше в політиці лишається. Проте він відновлює ці поля під час кожного повного звіряння, типово кожні 5
  хвилин, тоді як operator робив це лише під час наступного запуску: розклад, змінений у вебінтерфейсі,
  повертається назад за кілька хвилин. Задайте `kopia.schedule=""`, щоб натомість керувати розкладом у вебінтерфейсі.
- **Невідомі мітки дають попередження.** Operator мовчки ігнорував невідомі мітки `kopia.*` і небулеві значення.
  Watcher і далі їх приймає, але записує в лог попередження з назвою мітки й підказкою про ймовірний одрук.
  `validate --strict` і `run --strict` перетворюють попередження на помилки.
- **Відбиток перевіряється**, див. вище.
- **Видалені контейнери очищуються так, як задає `kopia.cleanup-on-remove`.** Operator назавжди лишав джерела
  видалених контейнерів у kopia server. Watcher типово ставить їх на паузу й нічого не видаляє. З
  `kopia.cleanup-on-remove=all` він видаляє їхні знімки й політику після `CLEANUP_GRACE`, зокрема знімки, які
  зробив operator (закріплені лишаються, якщо не задано `kopia.cleanup-delete-pinned=true`). `policy` видаляє
  лише політику джерела без знімків, тож джерела operator, які мають знімки, лишаються на паузі. Watcher очищує
  лише джерела, контейнери яких він бачив: контейнери, видалені до першого запуску watcher, лишають свої джерела
  як є. Див. [labels.md](labels.md#cleanup).
- **Шляхи, прибрані з `kopia.path`, втрачають свій контейнер**: їхні джерела ставляться на паузу й очищуються
  так, як задає `kopia.cleanup-on-remove`. Operator лишав їх як є.
- **Шлях, спільний для кількох контейнерів**, ставиться на паузу, лише коли всі вони зупинені.
- **Шляхи нормалізуються**: кінцева скісна риска більше не змушує kopia server відхиляти шлях.

## <a id="steps"></a>Кроки

У командах припускається, що watcher працює як сервіс `watcher` проєкту compose, як у
[прикладі](../../examples/docker-compose.yml).

1. **Зупиніть operator на Python** і видаліть його контейнер, щоб він не боровся з watcher за
   політики:

   ```bash
   docker compose stop kopia-operator
   docker compose rm -f kopia-operator
   ```

   У kopia server нічого не змінюється: джерела, їхні політики й знімки лишаються, як і паузи operator, доки не
   запрацює watcher.

2. **Підготуйте kopia server.** Перевірте [вимоги](../../README.uk.md#requirements). Якщо kopia server генерує свій
   сертифікат під час кожного запуску, спершу перейдіть на файли сертифіката на томі; тоді відбиток зміниться
   один раз. Візьміть відбиток із рядка логу `SERVER CERT SHA256:`.

3. **Додайте сервіс watcher** у свій файл compose (див. таблицю вище й приклад) і заповніть його
   середовище. Лишіть `HOST_PREFIX` таким, як був.

4. **Перевірте мітки** своїх контейнерів. Без запуску watcher:

   ```bash
   docker compose run --rm watcher validate --all
   docker compose run --rm watcher validate --container app --container db
   ```

   Якщо задано `KOPIA_SERVER_URL`, команда також перевіряє з'єднання, облікові дані й відбиток, а kopia server
   на її запит нормалізує кожен шлях і обчислює час наступних знімків для кожного розкладу. Виправте помилки; прочитайте
   попередження, які operator мовчки проігнорував би. Додайте `--strict`, щоб побачити, що відхилив би суворий
   режим. `validate` не перевіряє, чи шлях існує.

5. **Подивіться, що зробив би watcher**:

   ```bash
   docker compose run --rm watcher run --dry-run
   ```

   Він один раз звіряє кожен шлях і виводить для кожного джерела політику, яку записав би (нові джерела, зміни
   розкладу, паузи operator, які зняв би), час наступних запланованих знімків і очищення, яке виконав би.
   Він не показує знімків під час запуску чи зупинки, які поставив би в чергу. Він нічого не записує в kopia
   server чи `STATE_FILE` і завершується з кодом 1, якщо знайшов проблему.

6. **Запустіть watcher** і стежте за його логом:

   ```bash
   docker compose up -d watcher
   docker compose logs -f watcher
   ```

   Він чекає на kopia server, записує в лог «connected to kopia server» і «watching containers», а потім по рядку на
   кожну зміну, яку робить. Помилки називають контейнер або шлях. Два рядки підсумовують його запуск:

   - «first full reconcile»: скільки контейнерів він знайшов, у скількох увімкнено резервне копіювання, скільки
     шляхів це дає;
   - «first full reconcile done», коли для кожного з цих шляхів відбувся прохід: скільки джерел він зареєстрував,
     оновив, визнав актуальними, поставив на паузу, пропустив або на скількох зазнав невдачі. Якщо жоден
     контейнер не вмикає резервне копіювання, він додає підказку про мітку `kopia.enable`.

7. **Перевірте вебінтерфейс Kopia**:

   - Джерела — ті самі, що зареєстрував operator, під тим самим `user@host`, а не дублікати під новим
     шляхом чи хостом. Дублікати означають, що змінився `HOST_PREFIX` або ім'я хоста kopia server.
   - Джерела запущених контейнерів більше не на паузі; джерела зупинених — на паузі.
   - Розклад кожного джерела — той, що задає його мітка `kopia.schedule`.
   - Зберігання, стиснення та інші налаштування, задані вами у вебінтерфейсі, досі на місці.
   - Нові знімки мають опис із `kopia.description` або з імені контейнера, з тегами у квадратних
     дужках.

Щоб повернутися назад, зупиніть watcher і знову запустіть operator. Зміни watcher — це звичайні поля політики й
описи знімків; operator ігнорує описи й замінює політики під час наступних подій запуску, як і
раніше.
